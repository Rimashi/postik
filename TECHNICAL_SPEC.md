# Техническое задание

## 1. Общие положения

**Наименование:** PSME — информационная система публикации и обсуждения статей.

**Назначение работы:** учебный проект по дисциплине «Методология и практики DevOps».

**Основание для разработки:** задание лабораторной работы №1 и требования к сквозному проекту.

Проект является учебным веб-приложением и не ставит целью полное воспроизведение промышленной платформы публикаций.

## 2. Назначение и цели

Система предназначена для публикации пользовательских материалов, их просмотра и обсуждения.

Основные цели:

- хранить статьи и связанные данные в реляционной БД;
- предоставить веб-интерфейс и HTTP API;
- обеспечить регистрацию и аутентификацию пользователей;
- разделить публичные операции просмотра и действия авторизованных пользователей;
- реализовать содержательные ограничения предметной области.

## 3. Объект автоматизации и пользователи

Объект автоматизации — процесс публикации и обсуждения материалов в небольшом интернет-сообществе.

Категории пользователей:

- **гость** — просматривает опубликованные статьи и комментарии;
- **пользователь** — создаёт и редактирует собственные статьи, комментирует, голосует и сохраняет публикации;
- **модератор** — роль предусмотрена моделью для дальнейшего развития;
- **администратор** — имеет расширенные права и может удалять чужие публикации.

## 4. Требования к продукту

### 4.1. Функциональные требования

Система должна обеспечивать:

- регистрацию и вход по логину и паролю;
- создание, редактирование и удаление собственных публикаций;
- состояния публикации `draft`, `published`, `under_review`;
- категории и теги;
- просмотр публичной ленты;
- фильтрацию и сортировку ленты;
- комментарии и ответы на комментарии;
- лайки и дизлайки публикаций и комментариев;
- сохранение публикаций;
- загрузку изображений;
- статистику публикации;
- служебный endpoint проверки состояния приложения и БД.

### 4.2. Основные сущности

К основным связанным сущностям относятся `User`, `Post`, `Comment`, `Category` и `Tag`.
Полная схема приведена в `schema.dbml`.

### 4.3. Бизнес-правила

- публикацию может изменять её автор;
- удалить чужую публикацию может администратор;
- создавать публикации, комментарии, голоса и сохранения могут только авторизованные пользователи;
- один пользователь может иметь не более одного голоса на одну публикацию;
- значение голоса допускается только `1` или `-1`;
- один пользователь не может сохранить одну публикацию несколько раз;
- ответ на комментарий может ссылаться только на комментарий той же публикации;
- опубликованная лента содержит только публикации со статусом `published`.

### 4.4. Требования к хранению данных

Данные хранятся в PostgreSQL. Связи между сущностями реализуются внешними ключами и ассоциативной таблицей `post_tags`.
Пароли хранятся только в виде хеша.

### 4.5. Требования к конфигурации и безопасности

- адрес БД, секрет Flask и учётные данные первоначального администратора передаются через переменные окружения;
- файл `.env` не хранится в Git;
- в репозитории находится только `.env.example` без реальных секретов;
- операции, требующие входа, проверяются на серверной стороне;
- некорректные API-запросы должны возвращать понятный HTTP-ответ вместо аварийного завершения приложения.

### 4.6. Требования к интерфейсу и API

Система должна иметь HTML/CSS/JavaScript-интерфейс и HTTP API. Описание API хранится в `API.md`.

## 5. Состав работ

1. Подготовить модель данных.
2. Реализовать Flask-приложение и PostgreSQL-хранилище.
3. Реализовать аутентификацию.
4. Реализовать работу с публикациями и комментариями.
5. Добавить обработку некорректных запросов.
6. Перенести конфигурацию в переменные окружения.
7. Добавить `GET /api/health`.
8. Оформить документацию и Git-процесс.
9. Развернуть приложение в Linux-среде в рамках ЛР2.

## 6. Порядок контроля и приёмки

На демонстрации проверяются:

- запуск приложения;
- регистрация и вход;
- работа минимум трёх связанных сущностей;
- создание и просмотр публикации;
- реакция на некорректный запрос;
- `/api/health`;
- отсутствие `.env` в Git;
- история задачи, отдельной ветки, нескольких коммитов и Pull Request;
- наличие тега `v0.1.0`.
