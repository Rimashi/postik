# GitHub Actions и поставка проверенных образов

CI запускается из `.github/workflows/ci.yml` для pull request в `main`, push в `main` и ручного запуска, но **не развёртывает приложение на сервер**. Развёртывание — отдельный CD-процесс с проверкой релиза и подходящими правами.

Jobs `quality`, `tests`, `migrations`, `backup`, `dependencies`, `secrets`, `containers`, `images` независимы: каждый выполняет команды из `Makefile`. `ci-required` зависит от всех восьми результатов и требует `success`; если хотя бы один job упал, пропущен или отменён, gate не пройдёт. В `main` после успешного gate `publish` создаёт образы API и web, присваивает теги полного SHA коммита и публикует в GHCR. Публикация не выполняется на PR.

- Ruff: форматирование, статический анализ на ошибки/качество.
- Bandit: Python SAST-проверки на опасные конструкции.
- pytest/Node test: unit и HTTP-интеграционные сценарии, coverage ≥65% для Python.
- Alembic + PostgreSQL: последовательные миграции на чистой и заполненной БД.
- pg_dump/pg_restore: демонстрация восстановления после преднамеренного повреждения тестовых данных.
- pip-audit, npm audit: известные уязвимости зависимостей.
- Gitleaks: поиск секретов по истории Git.
- Trivy: полный отчёт по HIGH/CRITICAL для обоих Docker-образов сохраняется в `backend/reports/trivy-{api,web}.json`. Второй проход с `--ignore-unfixed` блокирует CI при HIGH/CRITICAL, для которых сканер знает исправленную версию (`trivy-{api,web}-fixable.json`). Остальные находки не считаются исправленными: их необходимо отслеживать и оценивать отдельно.

## Подключить GitHub

1. Создать/подключить репозиторий с исходниками БЕЗ `.env`, виртуальных окружений, образов и дампов.
2. `python3 scripts/setup_codeowners.py ВАШ_ЛОГИН_GITHUB`, зафиксировать полученный `.github/CODEOWNERS`.
3. Создать отдельную ветку и PR в `main`.
4. В Settings → Rules → Rulesets настроить обязательный PR, статус `Mandatory CI gate`, review владельцев критических файлов и запрет обхода правил. CODEOWNERS сам по себе не является защитой; на личном репозитории собственное согласование PR также не заменяет независимое ревью.
5. Исправить реальные ошибки CVE/уязвимостей, если сканер обнаружит их. Доказательство CI — реальный запуск в GitHub Actions, не YAML в архиве.
6. После успешного merge проверить Packages → GHCR и наличие тегов `sha-<COMMIT_SHA>`.

## Демонстрация отказа

В отдельной ветке изменить в `backend/app/main.py` увеличение счётчика просмотров `+ 1` на `+ 2`, открыть PR и убедиться в падении теста, а затем `Mandatory CI gate`. Не менять сам тест. Вернуть правильную логику — pipeline должен стать зелёным. Для проверки Gitleaks используйте только фиктивный тестовый токен и отдельную ветку, не реальные секреты. Если токен зафиксирован в истории, простое удаление файла не убирает историю коммитов; именно это и проверяет Gitleaks.

**Ограничения:** структура workflow проверялась локально; реальный GitHub run и публикацию GHCR необходимо выполнить в собственном репозитории. Надёжная защита критических файлов требует реального Ruleset/Branch protection и независимого ревью.
