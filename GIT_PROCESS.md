# Git-процесс

Основная ветка проекта — `main`.

Новая функциональность выполняется через:

```text
Issue -> feature-ветка -> несколько коммитов -> Pull Request -> проверка -> merge
```

## Пример для ЛР1

После первоначальной загрузки проекта можно провести через отдельную ветку небольшую функцию `GET /api/version`.

1. Создать Issue «Добавить endpoint версии приложения».
2. Создать ветку:

```bash
git switch main
git pull
git switch -c feature/version-endpoint
```

3. Сделать несколько осмысленных коммитов, например:

```text
add version endpoint
add version check to documentation
```

4. Отправить ветку:

```bash
git push -u origin feature/version-endpoint
```

5. Создать Pull Request в `main`, проверить вкладку `Files changed`, затем выполнить merge.

## Правила внесения изменений

Перед merge необходимо:

```bash
make check
```

Также необходимо проверить запуск приложения и `/api/health`.

Запрещается:

- коммитить `.env`, пароли, приватные SSH-ключи и дампы с секретами;
- запускать приложение от root;
- добавлять функциональность напрямую в `main`, если изменение выполняется как отдельная задача;
- открывать наружу порт PostgreSQL без необходимости;
- сливать изменение, которое не запускается или ломает основной сценарий.

После готовности первой версии:

```bash
git tag -a v0.1.0 -m "Laboratory work 1"
git push origin v0.1.0
```

> В официальном задании ЛР1 отдельно указан учебный конфликт слияния. В подготовленном репозитории он намеренно не имитируется автоматически: если преподаватель требует этот пункт буквально, его нужно выполнить и показать отдельно.
